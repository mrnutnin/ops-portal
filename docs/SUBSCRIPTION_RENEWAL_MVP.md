# Subscription Renewal MVP — แจ้งเตือนและยืนยันรับชำระภายนอก

สถานะ: พัฒนา MVP ใน ops-portal แล้ว; automated tests ผ่าน และ migrate เฉพาะไฟล์ใหม่ในฐาน ops_portal แล้ว (batch 7) ไม่ส่งสิทธิ์ลูกค้าจริง และยังรอ browser/ERP UAT กับ backup/restore

## 1. เป้าหมายและขอบเขต

Ops ช่วยติดตาม Instance ที่ต้องต่ออายุ → Admin เก็บเงินและออกเอกสารผ่านโปรแกรมบัญชีภายนอก → กลับมายืนยันรับชำระพร้อมหลักฐาน → ต่ออายุใน Ops → ส่งสิทธิ์ไปยัง Instance แบบ manual

### ทำใน MVP

- หน้า Admin แสดง Subscription ใกล้หมดอายุและหมดอายุ พร้อมรายการติดตามการเก็บเงิน
- เปิดรายการต่ออายุของแต่ละ Instance เพื่อบันทึกรอบบริการและเอกสารภายนอก
- Admin ยืนยันรับชำระพร้อมจำนวนเงิน วันที่รับ และหลักฐาน
- ต่ออายุหลังตรวจสอบ โดยแยกจากการยืนยันรับเงินและการส่งสิทธิ์
- แยกรอบบริการที่ชำระออกจากวันสิ้นสุดสิทธิ์ พร้อมผ่อนผัน 15 วันสำหรับการต่ออายุลูกค้าเดิม
- ประวัติผู้ดำเนินการ เวลา เหตุผล และ audit

### ไม่ทำใน MVP

- ไม่สร้างใบแจ้งหนี้ ใบวางบิล ใบเสร็จ หรือเอกสารภาษีใน Ops
- ไม่เชื่อม API โปรแกรมบัญชี ไม่ทำ Payment Gateway หรือให้ลูกค้าอัปโหลดเอง
- ไม่ส่งอีเมล/LINE ไม่ใช้ scheduler; คำนวณรายการเตือนเมื่อเปิดหน้า Ops
- ไม่คำนวณ VAT/หัก ณ ที่จ่าย ไม่ทำบัญชีลูกหนี้หรือกระทบยอดธนาคาร
- ไม่รองรับผ่อนชำระ คืนเงิน หรือปรับราคาอัตโนมัติ
- ไม่ต่ออายุ ส่งสิทธิ์ หรือระงับสิทธิ์อัตโนมัติ
- ไม่รวมการเปลี่ยน Plan/Quota/Add-on หรือ Trial conversion ในปุ่มต่ออายุ

โปรแกรมบัญชีภายนอกเป็นแหล่งอ้างอิงเอกสารและยอดทางบัญชี; บันทึกใน Ops เป็นหลักฐานการดำเนินงาน ไม่ใช่บัญชีลูกหนี้

## 2. สิ่งที่มีอยู่และจะนำกลับมาใช้

- `InstanceEntitlement`: Plan, ช่วงใช้งาน, status, cancel_at_period_end และ source_revision
- `AdminInstanceEntitlementController`: ฟอร์มสิทธิ์ การล็อกข้อมูล transaction และการเพิ่ม revision
- `TrialIssuanceService`: ขั้นตอน Trial conversion ที่มี validation และ audit; ไม่ข้ามขั้นตอนนี้
- `InstanceEntitlementDelivery`: enrollment และส่ง snapshot แบบ manual
- `OpsAuditLog`: บันทึกการเปลี่ยนแปลงและผู้ดำเนินการ
- Middleware Admin เดิมใน `routes/web.php`
- Private local disk ใน `config/filesystems.php`: `storage/app/private` ไม่ใช่ public disk
- UI รับและแสดงเวลา Asia/Bangkok แต่ฐานข้อมูลและ snapshot เก็บ UTC

MintERP มี delivery flow อยู่แล้ว ส่วน MintPOS/MintHRM ยังไม่มี delivery/enforcement adapter ตามเอกสารปัจจุบัน ห้ามแสดงว่าส่งสำเร็จเพียงเพราะบันทึกใน Ops แล้ว

## 3. ขั้นตอนใช้งาน

1. Admin เปิดหน้า “ติดตามต่ออายุ” และดูรายการใกล้ครบกำหนด/อยู่ช่วงผ่อนผัน/สิทธิ์หมดอายุ
2. เปิดรายการต่ออายุ ระบุ Instance รอบบริการใหม่ และยอดตามข้อตกลง
3. ออกใบแจ้งหนี้และเก็บเงินในโปรแกรมบัญชีภายนอก แล้วบันทึกเลขอ้างอิงกลับมา
4. เมื่อฝ่ายบัญชีตรวจรับแล้ว Admin กรอกยอดรับจริง วันที่รับ และแนบหลักฐาน จากนั้นกด “ยืนยันรับชำระ”
5. รายการแสดง “รับชำระแล้ว — รอต่ออายุ”; ขั้นนี้ยังไม่เปลี่ยนสิทธิ์
6. Admin ตรวจรอบบริการจริง วันสิ้นสุดสิทธิ์รวมผ่อนผัน และสิทธิ์ปัจจุบัน แล้วกด “ต่ออายุใน Ops” โดยต้องทำและส่งสิทธิ์ก่อนสิทธิ์เดิมหมด
7. รายการแสดง “ต่ออายุใน Ops แล้ว”; Admin ใช้ปุ่มส่งสิทธิ์เดิมแยกต่างหาก
8. แสดงผลส่ง revision ปัจจุบัน: ยังไม่ส่ง / ส่งไม่สำเร็จ / ปลายทางตอบรับ หรือยังไม่รองรับการส่ง

Admin คนเดียวสามารถบันทึกและยืนยันได้ใน MVP ไม่เพิ่ม workflow ผู้อนุมัติคนที่สอง แต่ต้องเก็บตัวตนและเวลา

## 4. หน้าจอและกฎการแจ้งเตือน

เพิ่มหน้า Admin เช่น `/admin/renewals` และลิงก์เปิดรายการจากหน้า Instance เดิม

| กลุ่ม | เงื่อนไข |
| --- | --- |
| ใกล้ครบกำหนด | paid Subscription ที่ `now < paid_period_end <= now + 15 วัน` |
| อยู่ช่วงผ่อนผัน | paid Subscription ที่ `paid_period_end <= now < expires_at` |
| สิทธิ์หมดอายุ | paid Subscription ที่ `expires_at <= now` |
| รอยืนยันชำระ | มีรายการต่ออายุสถานะ PENDING |
| รับชำระแล้ว รอต่ออายุ | มีรายการสถานะ CONFIRMED |
| ต่ออายุแล้ว | ประวัติรายการ APPLIED พร้อมผลส่งสิทธิ์แยกต่างหาก |

- เตือนล่วงหน้า 15 วันก่อนสิ้นสุดรอบที่ชำระ ไม่ใช่ก่อนสิ้นสุดระยะผ่อนผัน; ไม่ต้องสร้างหน้าตั้งค่า
- แสดงจำนวนวันเหลือก่อน readonly และเน้นรายการรับเงิน/ต่ออายุแล้วแต่ยังส่งสิทธิ์ไม่สำเร็จ
- กลุ่มเวลาและกลุ่มการเก็บเงินแสดงร่วมกันได้ ไม่ใช่ status เดียวกัน
- ใช้ช่วงเวลาจริงในการตัดสิน แล้วแสดงเวลาประเทศไทย; วันหมดอายุเป็นขอบเขต exclusive ตามระบบเดิม
- แสดงลูกค้า Product Instance/ref Plan วันสิ้นสุดรอบที่ชำระ วันครบกำหนดชำระ และวันสิ้นสุดสิทธิ์รวมผ่อนผันแยกกัน พร้อมลิงก์รายการ/สิทธิ์
- License และ Instance ที่ยังไม่มีสิทธิ์ไม่เข้ารายการต่ออายุ
- Trial แสดงคำเตือนแยกและลิงก์ conversion เดิม ไม่ถือเป็นยอดค้างชำระ
- แสดง SUSPENDED และ cancel_at_period_end ให้เห็นชัด ไม่ต่ออายุผ่าน flow ปกติจน Admin จัดการเหตุผลผ่านขั้นตอนสิทธิ์เดิม
- ลูกค้า/Product/Instance ที่ปิดใช้งานไม่อยู่คิวปกติ แต่ประวัติยังค้นหาได้
- ไม่มีราคาที่กำหนดไว้ไม่แปลว่าเป็นหนี้; ป้ายหมดอายุหมายถึงสิทธิ์หมดอายุ ไม่ใช่ค้างเงิน
- เรียงวันหมดอายุและใช้ pagination/filter ไม่โหลดประวัติทั้งหมด

### นโยบายรอบบริการและผ่อนผัน 15 วัน

- `period_start`/`period_end` คือรอบบริการจริงแบบ `[start, end)`; `paid_period_end` บน entitlement คือขอบเขตสิ้นสุดรอบที่ยืนยันชำระและนำไปใช้แล้ว ไม่ใช่วันที่รวมผ่อนผัน
- วันครบกำหนดชำระรอบถัดไปเริ่มต้นที่ `paid_period_end` (ชำระก่อนเริ่มรอบใหม่); ถ้าเอกสารบัญชีกำหนดวันอื่นให้บันทึก `payment_due_at` แยก โดยไม่เลื่อนสิทธิ์ตามวันเอกสาร
- `expires_at = paid_period_end + grace_days` โดยนโยบายต่ออายุลูกค้าเดิมใช้ `grace_days = 15`; เก็บค่าไว้กับสิทธิ์และ snapshot เพื่อให้ตรวจย้อนหลังได้
- ตัวอย่าง: รอบตุลาคมเริ่ม 1 ต.ค. 00:00 และสิ้นสุด 1 พ.ย. 00:00 เวลาไทย → ผ่อนผันจน 16 พ.ย. 00:00 → หากยังไม่ต่ออายุ ERP เข้า readonly เมื่อถึงเวลานั้น
- เมื่อชำระรอบพฤศจิกายน ขอบเขตรอบใหม่เป็น 1 พ.ย.–1 ธ.ค. และสิทธิ์สิ้นสุด 16 ธ.ค. ไม่เริ่มเดือนใหม่จากวันที่โอน และไม่บวกผ่อนผันสะสมจาก expires_at เดิม
- ผ่อนผันครั้งเดียวต่อรอบ การเปิดหน้า/สร้างรายการ/ติดตาม/กดส่งซ้ำไม่ขยับวันสิ้นสุดสิทธิ์
- ระยะผ่อนผันของรอบที่ใช้ปัจจุบันต้องบันทึกและส่ง ERP ไว้ก่อนหมดอายุ ไม่รอรับเงินรอบถัดไปแล้วจึงเพิ่ม 15 วัน
- Trial ไม่ได้ผ่อนผัน และรอบแรกหลัง Trial ต้องยืนยันรับเงินก่อนใช้ขั้นตอน conversion เดิม; ห้ามเปิด paid Subscription ให้ผู้ยังไม่ชำระเพียงเพื่อให้ผ่อนผัน
- การกำหนดยกเลิกเมื่อจบรอบต้องทบทวนวันสิ้นสุดสิทธิ์ให้ตรงรอบที่ชำระ ไม่เพิ่ม grace ให้รอบที่ยกเลิกโดยเงียบ ๆ; ไม่ปรับวันหรือส่งสิทธิ์อัตโนมัติ
- ERP ใช้ expires_at เดิมต่อไป ไม่ต้องเพิ่ม field grace ใน sync payload หรือเปลี่ยน middleware; ระยะผ่อนผันไม่ปลด SUSPENDED และไม่เปลี่ยน Plan/Quota/Add-on

## 5. ข้อมูลขั้นต่ำ

เพิ่มตารางเดียว เช่น `instance_renewals` โดยหนึ่งรายการผูกกับหนึ่ง Instance และหนึ่งรอบบริการ พร้อมเพิ่ม `paid_period_end` (nullable) และ `grace_days` (default 0) บน `instance_entitlements` เพื่อเก็บขอบเขตรอบปัจจุบันแยกจาก expires_at

| กลุ่ม | ข้อมูล |
| --- | --- |
| อ้างอิง | id, instance_id, เลขอ้างอิงเอกสารบัญชีภายนอก, หมายเหตุ |
| รอบบริการ | period_start, period_end, payment_due_at, grace_days, วันสิ้นสุดสิทธิ์ที่เสนอ, source_revision/รอบที่ชำระ/วันหมดอายุ ณ เปิดรายการ |
| ยอดเงิน | agreed_amount, received_amount แบบ decimal 2 ตำแหน่ง; THB ใน MVP ไม่ใช้ float |
| การรับชำระ | received_at, confirmed_by, confirmed_at |
| หลักฐาน | private path, ชื่อเดิม, MIME, ขนาด; หนึ่งไฟล์ PDF/JPEG/PNG ไม่เกิน 10 MB |
| ต่ออายุ | applied_by, applied_at, applied_revision, snapshot สิทธิ์ก่อน/หลัง |
| สถานะ/ประวัติ | PENDING / CONFIRMED / APPLIED / VOID, optimistic version, created_by, voided_by/at/reason, timestamps |
| กันรายการซ้ำ | nullable unique open_instance_id สำหรับ PENDING/CONFIRMED; ปล่อยว่างเมื่อ APPLIED/VOID |

- ยอดตามข้อตกลงและยอดรับจริงอาจไม่เท่ากัน เช่น หัก ณ ที่จ่าย; ต้องระบุเหตุผลและให้บัญชีภายนอกยืนยันว่าเคลียร์ยอดครบแล้ว ไม่ใช้สูตรเทียบยอดเอง
- ถ้ายังชำระไม่ครบ ให้คง PENDING; MVP ไม่บันทึกยอดผ่อนหลายครั้ง
- เลขอ้างอิงและหลักฐานต้องมีตอนยืนยัน ไม่บังคับว่าหมายเลขเอกสารห้ามซ้ำทั่วระบบ เพราะเอกสารเดียวอาจครอบคลุมหลาย Instance
- กรณีใบเสร็จรวมหลาย Instance ให้บันทึกยอดที่จัดสรรต่อ Instance และอ้างเอกสารเดียวกัน; Admin ตรวจยอดรวมกับบัญชีภายนอกเอง
- PENDING แก้รายละเอียดได้พร้อม audit; CONFIRMED ล็อกยอด/รอบ/เอกสาร/หลักฐาน
- แก้รายการ CONFIRMED ที่ผิดโดย VOID พร้อมเหตุผลแล้วสร้างใหม่ ไม่เขียนทับหลักฐานเดิม
- APPLIED เป็นประวัติถาวร ห้าม VOID แล้วลดสิทธิ์โดยอัตโนมัติ; การแก้สิทธิ์ใช้ flow เดิมพร้อม audit และการแก้เงินทำในบัญชีภายนอก
- ไม่ลบประวัติเมื่อปิดใช้งาน Instance และไม่เพิ่มตารางเอกสาร/การรับเงินทั่วไปใน MVP
- Migration ไม่เปลี่ยน expires_at ของข้อมูลเดิมและไม่เดาวันชำระ: ถ้า paid_period_end ยังว่าง ให้ใช้ expires_at เป็นขอบเขตเดิมเพื่อเตือน พร้อมป้าย “ยังไม่แยกรอบบริการ/ผ่อนผัน”
- เปิดนโยบายให้ลูกค้าเดิมโดย Admin ตรวจรอบที่ชำระและหลักฐาน/เอกสารอ้างอิง แล้วบันทึก paid_period_end, grace_days และ expires_at พร้อม audit/revision ก่อนกดส่งแยก; ทำก่อนวันหมดอายุเดิมและกันการเปิดนโยบายซ้ำ
- ทุก flow ที่แก้ช่วงเวลา/mode/cancellation รวมถึงฟอร์มทั่วไปและ Trial conversion ต้องรักษาความสอดคล้องของ paid_period_end/grace_days/expires_at; ห้ามเหลือข้อมูลรอบ paid เก่าบน Trial/License หรือป้ายชำระแล้วที่ไม่มีหลักฐาน

## 6. กฎยืนยันและต่ออายุ

### ยืนยันรับชำระ

- เฉพาะ Admin ที่ active และผ่าน authentication/password-change middleware เดิม
- ต้องมีรายการ PENDING, รอบบริการถูกต้อง, ยอดบวก, วันที่รับไม่อยู่อนาคต, เลขเอกสาร และหลักฐานที่บันทึกสำเร็จ
- ตรวจยอดกับโปรแกรมบัญชีจริงก่อนยืนยัน; การแนบสลิปเพียงอย่างเดียวไม่เท่ากับตรวจรับเงิน
- บันทึก confirmation และ audit ใน transaction; ไม่แก้ entitlement และไม่ส่ง network request
- กดซ้ำ/ส่ง request ซ้ำต้องไม่สร้าง confirmation ซ้ำ

### ต่ออายุใน Ops

- รับได้เฉพาะ CONFIRMED ที่ยังไม่ APPLIED และ paid Subscription ที่ไม่ SUSPENDED/ไม่กำหนดยกเลิก
- ตรวจลูกค้า/Product/Instance ยังเปิดใช้งาน และ Plan อยู่ใน Product เดียวกัน
- ล็อก Instance, entitlement และรายการด้วยลำดับเดียวกันทุก caller; update entitlement, applied_revision และ audit ใน transaction เดียว
- ถ้า revision หรือสิทธิ์เปลี่ยนจากที่ตรวจไว้ ให้หยุดและแจ้ง Admin ทบทวน ไม่ overwrite เงียบ ๆ
- ต่อเนื่อง: รอบใหม่เริ่มตรง paid_period_end เดิม (หรือขอบเขตเดิมที่ Admin ตรวจยืนยันสำหรับข้อมูล legacy) ไม่ใช่ expires_at ที่รวมผ่อนผัน; คง starts_at เดิม
- ถ้าขาดช่วงบริการ: รอบใหม่เริ่มหลังขอบเขตรอบที่ชำระเดิมและไม่หลังเวลาต่ออายุ; Admin ยืนยันช่วงบริการใหม่ และตรวจว่าการตั้ง starts_at ใหม่ไม่ตัดสิทธิ์ที่ยังใช้งานอยู่
- period_end ต้องหลัง period_start, หลังขอบเขตรอบที่ชำระเดิม และหลังเวลาปัจจุบัน; expires_at ใหม่ต้องไม่ลดลงจากเดิมผ่าน flow ต่ออายุ
- เมื่อต่ออายุ ให้ตั้ง paid_period_end = period_end และ expires_at = period_end + 15 วันตามนโยบาย ไม่บวกเดือน/วันจากวันโอนหรือ expires_at เดิม
- ไม่รับรอบเริ่มอนาคตที่ขาดช่วงใน MVP เพราะมี entitlement ปัจจุบันเพียงชุดเดียว; นัด Admin มาต่อเมื่อเริ่มรอบ หรือเพิ่ม scheduling ภายหลัง
- คง Plan, overrides, modules และ Add-on เดิม เพิ่ม source_revision เพียงครั้งเดียว
- กดซ้ำและสอง Admin ทำพร้อมกันต้องไม่ต่ออายุซ้ำ
- ฟอร์มสิทธิ์เดิมยังใช้แก้ข้อยกเว้นได้ แต่ไม่แสดงว่าเป็นการรับเงิน และห้ามเปลี่ยนรายการให้ APPLIED เพียงเพราะวันหมดอายุตรงกัน

### ส่งสิทธิ์

- ใช้ delivery เดิมแบบ manual หลัง commit เท่านั้น ไม่ผูกความสำเร็จการรับเงินกับ network
- ส่งล้มเหลวไม่ย้อนการรับเงิน/การต่ออายุใน Ops; Admin ส่งซ้ำผ่าน flow เดิม
- ผลตอบรับต้องตรง revision และปลายทางปัจจุบัน ไม่ใช้ audit สำเร็จเก่ามาแสดงว่า sync ล่าสุดแล้ว
- ไม่เชื่อมฐานข้อมูล Product โดยตรง และคง approval/network/UAT gates เดิม

## 7. หลักฐานและ audit

- ตรวจชนิดไฟล์จากเนื้อหาและขนาด ไม่เชื่อ filename; ไม่รับ SVG/HTML/ไฟล์ executable
- ตั้งชื่อไฟล์จัดเก็บแบบสุ่มบน private disk เท่านั้น
- ดาวน์โหลดผ่าน authenticated Admin controller ที่ตรวจสิทธิ์และความสัมพันธ์กับรายการ ใช้ attachment response; ไม่เปิด public URL
- แยกชื่อเดิมที่ใช้แสดงออกจาก path และ escape ข้อมูลบนหน้าจอ
- ถ้า upload/write ล้มเหลว ห้ามยืนยัน; ถ้า DB transaction ล้มเหลวให้จัดการไฟล์ที่เพิ่งสร้างเพื่อไม่ทิ้ง orphan
- Audit การสร้าง/แก้รายการ ยืนยัน VOID และต่ออายุ พร้อม actor, เวลา, เหตุผล และ revision
- ไม่บันทึกเนื้อหาไฟล์หรือ secret ลง audit/log
- สำรองฐานข้อมูลพร้อม private files; กำหนดผู้เข้าถึงและนโยบายเก็บรักษาก่อนใช้งานจริง

## 9. เกณฑ์ส่งมอบ

- Admin เห็น Instance ที่ต้องติดตามล่วงหน้า 15 วันและไปเก็บเงินภายนอกได้โดยไม่ต้องคำนวณวันเอง
- รอบบริการที่ชำระและวันสิ้นสุดสิทธิ์รวมผ่อนผัน 15 วันแสดงแยกกัน ลูกค้าเดิมไม่เข้า readonly ระหว่างผ่อนผันเมื่อ ERP รับ snapshot แล้ว และไม่มีการขยายสิทธิ์ไม่สิ้นสุด
- ตรวจย้อนหลังได้ว่าใครยืนยันเงิน รอบไหน ยอดเท่าไร เอกสารและหลักฐานอะไร
- รับเงินแล้วไม่เปิดสิทธิ์อัตโนมัติ; ต่ออายุแล้วไม่อ้างว่าปลายทางอัปเดตโดยไม่มีผลส่งจริง
- การส่งซ้ำ/กดซ้ำไม่ทำให้รับเงินหรือต่ออายุซ้ำ และไม่มีหลักฐานเข้าถึงผ่าน public URL
- ไม่มีใบแจ้งหนี้/ระบบภาษี/การรับเงินออนไลน์ซ้ำกับโปรแกรมบัญชีภายนอก

## 10. เปิดใช้งานและ UAT ที่ยังต้องทำ

### ติดตั้งในสภาพแวดล้อมทดสอบก่อน

1. สำรองฐานข้อมูล Ops และ `storage/app/private` ด้วยสิทธิ์เข้าถึงที่จำกัด
2. Deploy โค้ด แล้วรัน `php artisan migrate` และ `php artisan route:clear` ใน environment ที่ผู้ดูแลตรวจอนุมัติแล้ว; migration นี้ไม่เลื่อน expires_at ของลูกค้าเดิม
3. ตรวจสิทธิ์เขียน private disk และตั้ง PHP/web-server upload limits ให้รองรับไฟล์ 10 MB พร้อม multipart overhead; private directory ห้าม expose ผ่าน web server
4. เข้า `/admin/renewals` ด้วย Admin; การเตือนเป็นรายการบนหน้า ไม่มีอีเมลหรือ scheduler
5. ลูกค้าเดิมที่ยังไม่แยกรอบ: เปิดรายการชนิด GRACE ใส่ช่วงสิทธิ์เดิม ยืนยันเอกสาร/หลักฐานที่ชำระแล้ว และนำไปใช้ก่อนสิทธิ์เดิมหมด จากนั้นส่งผ่านหน้า Instance แยกต่างหาก
6. รอบถัดไป: เปิด RENEWAL โดยเริ่มจาก paid_period_end เดิม; กรอก period_end ตามเดือนปฏิทิน/สัญญา ไม่คิดจากวันที่โอน
7. Trial: เปิด TRIAL และยืนยันเงินก่อนเลือกหมายเลขรายการนั้นในฟอร์ม conversion เดิม; paid_expires_at ต้องตรง period_end และรอบแรกมี grace_days = 0
8. หาก CONFIRMED แล้ว revision เปลี่ยน ให้ VOID พร้อมเหตุผลแล้วสร้างรายการใหม่; หลักฐานเดิมยังคงอยู่
9. APPLIED แล้วส่งล้มเหลว ให้ส่งซ้ำ ไม่รับเงิน/ต่ออายุซ้ำ ไม่ย้อนบันทึกเงิน
